# Nexus security architecture

Nexus enforces sensitive workflows server-side: authenticated identity, tenant/client scope, permission/policy evaluation, audit history and verifiable outcomes. Browser permission checks improve UX only.

Supabase service-role access is backend-only. MongoDB queries for client data must retain explicit server-side scope. Cross-tenant access is release-blocking. The shared record-scope guard returns the same generic `404` for a missing and a foreign record, including routes that supply a human-friendly internal resource label, so response text cannot become an ownership oracle. The current verification backlog and production controls are maintained in `SECURITY_REVIEW.md` and `NEXUS_ARCHITECTURE_PLAN.md`.

## Identity and session boundary

Nexus JWTs carry a signed session-generation claim and an issued-token identifier. Every authenticated request resolves the active user record server-side and compares that generation before returning an identity to a route. Password changes, TOTP disablement, technician archive/offboarding and the authenticated `POST /api/auth/sessions/revoke-all` control increment the MongoDB `users.session_version` value, immediately invalidating every earlier token. This applies equally to the supported browser PDF query-token compatibility path because it uses the canonical active-token resolver. Existing accounts and pre-generation legacy tokens remain generation zero until an account-security event advances them; a deployment should progressively rotate those legacy sessions through normal sign-in rather than weakening the new boundary.

## Nexus Verify boundary

Nexus Verify records sensitive-request context, independently scoped challenge/factor evidence, approval decisions and provider hand-off history in MongoDB. A recorded challenge never implies a message was delivered. A technician-entered evidence reference is explicitly stored as an operator attestation, not as a cryptographic or provider assertion. Verification request IDs are masked as not-found outside the caller's client scope, and a foreign ID submitted to the provider gate receives the same customer-bound response as an unusable request, so recovery activity cannot be enumerated across customers. High-risk approval is denied when the approver created the request or recorded any verification factor, including factors in the current multi-factor representation. A protected provider action can reserve a request only when every required factor is current, connector-verified and represented by the server-derived `verification.execution_eligible` flag; otherwise it fails closed with a human-safe explanation. For Microsoft actions, the request must also retain an immutable `provider_target` containing the exact Entra tenant ID, provider user ID and UPN; the execution gate rebuilds its target from the protected action path and compares those stable identifiers atomically before the provider call. A display name never authorises a Microsoft reset, sign-in state change or offboarding action. The browser may guide this workflow, but it cannot set eligibility, alter the stored target or call a provider action around the execution gate.

## Workflow automation boundary

Automation is an execution path, not a scope bypass. Client-scoped workflows match only events carrying the same stable `client_id`; events with conflicting envelope and payload client IDs do not run. Explicitly global workflows remain available for MSP-wide operating procedures, but their definition, management and manual execution require global scope. A durable run preserves client, tenant and correlation provenance. Before a worker reads, writes, notes or compensates a ticket or device, it applies the run's authoritative `client_id` to the database filter and fails safely when ownership cannot be proven. Ticket-note creation also holds a short-lived parent-ticket lock: both supported ticket customer-move paths fail with a retryable conflict until that child-note write is complete, preventing audit evidence from being split across client scopes. Approval, retry, reject and compensation controls load the run through the same masked client-scope boundary used by normal workflow reads.

## Operational notification-channel boundary

Slack, Teams and Discord incoming webhook URLs are bearer-style delivery credentials. `notify_channels` stores each destination encrypted at rest and the browser receives only safe configuration metadata, never a reusable URL. Managing, testing and removing an operational notification channel is restricted to a revalidated administrator account and creates central activity evidence; destination-test failures are deliberately generic so provider URLs do not escape in an error response. Legacy plain-text channel URLs are validated and upgraded only inside a trusted server-side delivery path, then removed from the stored record. The present product surface advertises only `ticket_created`, because it is the event Nexus currently publishes and tests; a new event type must gain a server-side producer and end-to-end delivery coverage before it can be configured.

## Knowledge runbook boundary

Knowledge procedures promoted from a resolved ticket resolve that ticket through the shared masked record-scope guard before any ticket notes or AI context are read. The resulting runbook stores the stable source-ticket, client and tenant identifiers; suggestions, library reads, feedback and edits remain within that client boundary. Historic ticket-derived records without a client binding fail closed for restricted users until their source ticket is safely revisited and lazily repaired. The former `/automation` surface and generic `/runbooks` create/update/delete/execute routes are retired with an explicit `410`: simulated cards may not become an ungoverned execution path. All material automation must use the governed Workflow Automation service, with simulation, approval, durable run and audit evidence.

Managed Assets intelligence (fleet summaries and the smart inbox) is derived only from the authenticated technician's scoped device and ticket records. Direct device dossier and Time Machine reads resolve the canonical asset through the masked record-scope guard before loading operational history; the site map scopes its aggregation before returning customer location or availability data. Device Compare likewise treats its request body as untrusted: every requested device is resolved through the same guard before inventory or correlated ticket metrics are read, and those metrics additionally retain the canonical device client binding. A missing asset and a foreign asset return the same response. The legacy `/bulk-actions` compatibility API is retired because it could report simulated completion without the managed Agent boundary; bulk work must use the governed Managed Assets endpoint. The UI may derive display counts from the already scoped device directory for consistency, but it is never the authorisation boundary.

## Network and bandwidth boundary

Network sites are authorised by the stable Nexus `network_sites.id`, never by the mutable UniFi logical site alias. Every child topology, WLAN, DPI, controller sync, bandwidth and alert route first proves that parent boundary; foreign IDs are masked as `404` and denied scope attempts are recorded. Existing module grants such as `permissions.networking.view/edit/delete` are enforced server-side so a direct API caller cannot rely on the browser hiding controls. Direct UniFi controllers are client- and tenant-bound before any provider request, cannot be reassigned by an ordinary update, and store only encrypted API credentials; legacy plaintext is migrated only after both boundaries are proven. Controller URLs are clean HTTP(S) origins with no embedded credentials, path, query or fragment and cannot target loopback, link-local, multicast, unspecified, ambiguous numeric, or other non-global IP addresses without a production `NEXUS_UNIFI_ALLOWED_HOSTS` allowlist.

UniFi Site Manager is a separately named server-only credential in the existing settings envelope. A bound `site_manager_tenant_id` gates every Site Manager route, action history and integration-status tile. Legacy unowned Site Manager credentials are never claimed by a read: a tenant operator must explicitly re-save the key to bind and encrypt the connection, while a tenantless legacy system actor remains only a controlled compatibility path. Provider base URLs are fixed to the official `api.ui.com` v1/EA origins, redirects are disabled, and raw provider payloads and historic action results are never returned. Client links use provider-verified metadata, tenant-scoped writes, and a unique partial index on `clients.unifi_site_id`; changing a client link requires an explicit unlink before a new site is assigned. `unifi_site_cache` is derived data keyed by both Nexus `client_id` and provider `site_id`.

## RustDesk provider boundary

The legacy RustDesk live API uses only a saved, server-owned provider origin and encrypted credential; it never accepts a request-supplied server URL or token for live probes. Provider configuration, live peer inventory, sync and audit operations require the Remote Access configuration permission and global scope. A saved RustDesk origin must be an HTTP(S) origin without a path, credentials, query or fragment, and cannot target loopback, link-local, multicast, unspecified or ambiguous numeric addresses. Deployments may additionally set `NEXUS_RUSTDESK_ALLOWED_HOSTS` to an exact comma-separated hostname allowlist. Live status polling is restricted to RustDesk IDs associated with the caller's scoped Nexus assets. Raw provider payloads stay server-side; their credential-shaped fields are redacted before persistence and they are not returned by registry APIs. Sync only creates or updates provider records once a single client-owned managed asset establishes canonical ownership. The scheduled auto-sync uses that same governed reconciliation service with a server-only system actor rather than bypassing scope and ownership checks. Portal remote-session audits and PDFs require an existing remote-session permission and use the caller's record scope before any audit data is read or rendered.

## Recurring billing boundary

Recurring invoices are client-scoped financial templates. Listing, statistics, record reads, history, create, update, delete, duplication, provider-usage toggles and manual generation all apply the authenticated user's client scope on the server. Foreign record IDs deliberately resolve as `404` after a scope-denial audit so technicians cannot enumerate another client's billing data. A recurring invoice cannot be reassigned to a different client through an update, and template application checks the target client before touching shared template-usage metadata. Scheduler status and manual scheduler runs are cross-client operations and require an explicitly global scope; the background scheduler calls the same governed generation helper using a labelled server-owned system actor. An empty scoped read never seeds or overwrites demo billing data.

## Invoice and payment boundary

Invoice mutations prove the stored source client scope before any financial state is read or changed. Split billing also proves the scope of every payer client before it can create payer invoices; moves prove both source and target scope, and reject issued, paid, split, ticket-conflicting or contract-conflicting records. Contract generation, manual payments, voids, Stripe checkout/status, Xero invoice sync and billing-profile reads/writes all apply the same client boundary. A Stripe checkout session is persisted and then accepted only for its original invoice, preventing a session ID from being replayed against another invoice. Reconciliation summaries are scoped; a settlement changes a fleet-wide batch and is therefore reserved for explicitly global operators. Xero and Stripe connection settings require the accounting-integration action plus global scope, redact provider credentials on read, and write configuration activity evidence. Xero callbacks require a server-only HMAC key and use a provider-event idempotency ledger.

Public invoice payment links are short-lived bearer capabilities, not a second invoice API. A link is bound at creation to one invoice, its client, collection, currency and current balance; every public method checks expiry, revocation, invoice ownership/collection consistency and collectability. Public card and BECS initiation creates a Nexus-owned payment transaction before handing off to Stripe, uses only a deployment-owned return origin, and does not trust browser input or provider metadata to choose an invoice or amount. Only a signed Stripe callback may settle a card/direct-debit payment. Settlement accepts a strict event/object/status allowlist, proves the existing transaction, invoice, amount and currency binding, performs an optimistic invoice write, and releases the idempotency gate for a safe provider retry if that write races. Public confirmation is read-only and session-bound. Bank-transfer claims remain awaiting confirmation until a scoped, permissioned operator confirms the same bound invoice. Operator list views deliberately redact bearer tokens and provider-session identifiers; billing-portal configuration and customer-portal sessions have their own action, scope and audit boundaries.

Portal checkout uses that same payment-link reservation and transaction binding rather than a parallel Stripe path. Browser input cannot select a different origin, amount, currency or idempotency key; the server resolves one canonical, client-scoped invoice collection before creating or reusing the provider session. Xero mirror invoices, estimates and recurring templates follow the same client/action/version boundary. Restricted users see only their scoped financial records and dashboards, while integration-wide sync, chart-of-accounts and reconciliation operations require an explicitly global finance/integration action.

Legacy commercial controls are also governed rather than trusted because they are older screens. Recurring smart-billing operations claim a period and use state/version/client-bound writes before sending or consolidating billing streams. Global product catalogue and price-kit changes require the dedicated `billing.catalogue.pricing.manage` action plus global scope; client price books and ticket kit application resolve the client/ticket server-side. Organisation-wide finance analytics require `billing.analytics.view` plus global scope. Late-payment email routes accept stable invoice/payment identifiers only and derive recipients, amounts and payment links from canonical records before auditable delivery. Finance AI analysis is scope-checked, receives minimised structural data only, and retains a non-AI fallback.

## Commercial document-template boundary

Invoice, estimate, statement and QBR templates are organisation-wide commercial configuration, not client-scoped documents. Their management endpoints require the explicit `billing.document_template.manage` action and an explicitly global operator scope; template creation, cloning, editing, deletion and default selection create central activity evidence without copying template content into audit logs. A single per-document-type MongoDB settings pointer is authoritative for the selected default, so default selection is one atomic write rather than a clear-all/update-many sequence. Legacy `is_default` flags remain compatibility projections only. The invoice PDF path still proves the source invoice's client scope and resolves its default through that pointer.

## Browser PDF navigation compatibility boundary

Native browser PDF previews/downloads currently use a query parameter because a direct navigation cannot consistently attach the Nexus Bearer header. That parameter is a temporary compatibility transport, not a second authentication path: it resolves through the same canonical signed-token and active-account check as `get_current_user`, then enforces the appropriate action permission (`billing.portal.view` for a client financial document, `billing.document_template.manage` plus global scope for a template preview) and the normal client/global scope. Denied action and scope attempts retain the normal central denial evidence. PDF responses are private/no-store and set `Referrer-Policy: no-referrer` to reduce caching and referrer disclosure while this compatibility flow exists.

Invoice, estimate, contract and purchase-order callers now use the server-issued `POST /api/document-pdf-capabilities` flow. It returns a five-minute opaque `pdfc_` browser capability and a relative PDF path, never a technician JWT. Nexus stores only a SHA-256 hash plus the actor, tenant, client, site, source collection, document ID/type, delivery mode and expiry evidence; the native expiry timestamp has a MongoDB TTL index. Each use reloads the active actor, confirms the permission, source document, client/site/tenant scope and preview/download mode, then records bounded use evidence. A fresh download capability is requested at the moment of download rather than reusing a potentially expired preview. The legacy JWT query path remains only for unsupported specialty preview families (templates, themes, reports and comparable document types); no new document route may adopt it, and those families need their own object-bound capability contracts before the compatibility path can be removed.

## Yeastar billing and Voice boundary

Yeastar PBX records, billing snapshots, sync history and Voice-workspace activity are client-scoped. Recalculation only processes PBXs in the caller's client scope and creates whole-fleet summary records only for explicitly global operators; a single-client activity record carries that client ID, while multi-client global summaries remain global. Extension overrides use canonical `pbx_id:extension_number` identifiers: Nexus resolves the parent PBX and enforces its client scope before reading or upserting the override. New and updated override records retain client and PBX provenance. Foreign PBX IDs return a masked `404`, and malformed/bare keys fail before any override database access.
