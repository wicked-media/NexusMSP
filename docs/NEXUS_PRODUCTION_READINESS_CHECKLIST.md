## Current cycle record — 2026-10-13

1. **Closed the buildable half of the last Release 1 queue item.** Roadmap item 5 asks to rehearse `Mongo/uploads restore` *and* `immutable application rollback`. The capture-and-restore rehearsal already existed (`scripts/Smoke-Test-NexusDockerRecovery.ps1`); the application half had only a written procedure. `scripts/Test-NexusApplicationRollback.ps1` now rehearses it on a disposable Compose project and emits retained evidence.
2. **What the drill proves, and what it does not.** It proves a rollback moves the running stack between two genuinely different immutable image identities and lands on the exact previous one, that the API is healthy afterwards, that seeded database and upload markers survive an application-only rollback, that a mutable `:latest` reference is still refused, and that `-ValidateOnly` changes nothing. It deliberately does not rehearse database migration rollback (a per-migration procedure that runs before older images start) and does not version-discriminate the web tier; both exclusions are disclosed in the script and the runbook rather than implied.
3. **`Deploy-NexusImageTag.ps1` gained `-SkipPull`** so a host that stages images ahead of a change window (air-gapped, or pre-loaded) can roll without a registry round-trip. It fails closed if the reference is not present locally and does not relax the immutable-reference checks.
4. **Not re-verifiable in this environment:** the drill needs a Docker host and PowerShell, neither of which exists in the authoring environment, exactly as with the recovery drill. It is verified here by reading plus a deterministic conformance test that fails when the script, the pin script's guards, the referenced runbooks and this checklist row drift apart. Running the drill and retaining its evidence remains a deployment-host action.
5. **Next priority:** the remaining Release 1 queue items are operational — deployment-host recovery, rollback and migration-drill evidence, the named rollback decision owner, and provider sandbox acceptance — so no new module is built until those are evidenced.
6. **Database-migration ledger and gate added.** Data-shape changes previously ran unversioned on every boot (`backfill_legacy_event_metadata`, `backfill_event_integrity` and the `ensure_*_indexes` family), each logged and then ignored, so nothing recorded which changes a database had received and a rolled-back image could start against a database a newer release had already migrated forward. `backend/app/services/schema_migrations.py` now keeps an ordered ledger in the `schema_migrations` collection and `backend/scripts/nexus_migrate.py` — shipped inside the API image — is the operator interface. An applied migration's recorded description is part of its identity, so editing one is `drifted`; a row for a migration this release does not define is `unknown`; both make the database incompatible and are blocking, while `pending` is reported and is deliberately not fatal, because the previous release is still serving until the change window applies it. The API's startup gate and `/api/ready` refuse an incompatible database in a production runtime, and `NEXUS_ALLOW_SCHEMA_MISMATCH=1` is the explicit break-glass acknowledgement for a deliberate recovery-capture restore. The registry's only migration, `0001-adopt-prelaunch-event-backfills`, adopts the existing boot backfills instead of reimplementing them and declares no down path with a stated reason, so rolling it back refuses before changing anything and points at the recovery capture.
7. **Verified here, and not here.** `backend/tests/test_schema_migrations.py` passes 21 tests covering the ledger, the apply/adopt/rollback paths, the irreversible refusal, drift and unknown detection, the CLI's exit codes (0 applied or compatible, 1 refused, 2 usage) and the refusal's own rendering; it forms part of the deterministic backend gate. The operator CLI was also run against a disposable real MongoDB database: `--apply` recorded the migration, `--status` reported the database compatible, and `--rollback-all` refused with exit 1 and left the ledger unchanged. `scripts/Test-NexusMigrationRollback.ps1` cannot execute in the authoring environment because it needs Docker and PowerShell, exactly as with the recovery and application-rollback drills; it is verified by reading plus a deterministic conformance test, and running it on the deployment host remains outstanding.

8. **First reversible migration added, and the drill now rehearses a real rollback.** The ledger previously held only an irreversible migration, so database rollback was still a restore decision rather than a command. Auditing the event backbone found a concrete, reversible gap: `purge_expired_events` selects `platform_events` by `retention_until <= now` and sorts by that same field from the six-hourly retention loop, while `ensure_event_backbone_indexes` covered five other access paths on that collection and never this one, so every retention pass was a collection scan plus an in-memory sort over the platform's fastest-growing collection. `0002-index-platform-event-retention` creates that index, and its down path drops it, restoring the previous index set exactly. The index is created only by the ledger, deliberately not by the boot-time index family: an index the API recreated on every start could not be rolled back, and a deterministic test fails if the boot path ever starts recreating a ledger-owned index. `scripts/Test-NexusMigrationRollback.ps1` now performs the rehearsal for real — it reads the index back from MongoDB, rolls the migration back through the shipped CLI, requires the effect to be gone and `--status` to report the migration pending again, then re-applies it — and records each step plus the rollback duration in the retained evidence.

9. **Verified here, and not here.** `backend/tests/test_schema_migrations.py` now passes 27 tests, adding the reversible registry entry, the exact create/drop inverse in both directions (including a tolerated already-missing index and a refusal to tolerate any other driver failure), the guard that the boot index family must not recreate a ledger-owned index, and a CLI rollback that leaves the irreversible migration recorded. The operator CLI was also driven against a disposable local MongoDB database exactly as a change window runs it: `--apply` created the index and recorded both rows, `--rollback-to 0001-adopt-prelaunch-event-backfills` dropped the index and removed only the reversible row, re-running the down path against the already-missing index was tolerated, and re-applying restored both. `explain` on the purge query confirmed both the gap and the fix on that server: `SORT` + `COLLSCAN` without the index and `LIMIT` + `FETCH` + `IXSCAN` with it. `scripts/Test-NexusMigrationRollback.ps1` still cannot execute in the authoring environment because it needs Docker and PowerShell, exactly as with the recovery and application-rollback drills, so the new rehearsal is verified here by reading, by a lexer-aware structural check and by its conformance test; running it and retaining its evidence remains a deployment-host action.
