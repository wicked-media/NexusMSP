# Nexus data ownership registry

Product related-record history (`GET /products/{id}/related-records`) is an ephemeral, tenant/client-scoped projection of MongoDB tickets, purchase orders and invoices using stable product IDs. No secondary authoritative store is created. Each source retains its historical line prices and quantities. Results are bounded to 100 records per domain with truncation disclosed. This is not a complete price-change audit or a reconstructed history of deleted records.

Status: initial audit baseline, 2026-08-14. This is a classification document, not a migration directive.

Ticket handover (`GET /tickets/{id}/handover`) is a read-only, ephemeral projection of the authorised parent ticket, tenant-scoped `ticket_comments` and same-client child tickets. It creates no collection, reading receipt, last-view marker or AI summary record. Existing records remain authoritative. Results are bounded and omissions are disclosed; legacy notes missing tenant ownership are not implicitly imported into an explicitly named tenant.

Ticket Context (`GET /ticket-enrichment/{id}`) is a read-only, ephemeral projection of the authorised ticket, same-client ticket records, the linked client and device records, and active contracts. It creates no score, forecast, health value or synthetic activity. Missing client linkage is explicitly marked partial, and all source reads use the caller's platform tenant and client scope.

TLS ingress certificate and ACME account material (Docker volume `nexus-caddy-data`) is deployment infrastructure state owned by the host certificate process. It is not Nexus business data, is never included in recovery packages, and is renewed automatically by the ingress or replaced through the approved certificate process.

## Tenant partition compatibility

New tenant-aware Nexus read and write paths use the authenticated actor's stable `tenant_id` before applying client or site scope. The Control Plane overview, cross-platform Microsoft search, Microsoft readiness/tenant registry and recent-activity evidence paths explicitly apply this partition before returning Nexus-owned operational data. Microsoft provider documents retain their established client-to-provider tenant boundary because their `tenant_id` is an Entra tenant ID, not the Nexus platform partition; Control Plane visibility is therefore derived through platform-scoped Nexus clients plus stable CIPP, Microsoft onboarding-registry and verified-provider mappings. A missing or ambiguous mapping produces no provider evidence rather than a cross-tenant result. The existing single-installation records with no tenant marker remain visible only inside the documented `nexus-local` partition; they are not visible to an explicitly tenant-bound actor. Before an external multi-tenant rollout, identity provisioning must persist a server-derived tenant ID for every user and new tenant-owned record. This is a prerequisite for onboarding another MSP tenant, not permission for a blind business-data migration.

## Required placement decision

Use PostgreSQL when a new domain needs transactional, relational, constrained business truth. Use MongoDB for variable-shape ingestion, telemetry, snapshots and document-centric retrieval. Add the decision and any cache/replica semantics here before introducing the new store.

# Observability data

Prometheus, Tempo, Loki, Alertmanager, and Grafana hold derived operational
telemetry only. MongoDB remains the authoritative business-data store. Metrics,
traces, logs, alert state, and dashboards are non-authoritative operational
evidence with bounded retention; they must not be used as relationship keys or
to reconstruct customer records. Metric labels and trace attributes exclude
tenant, client, user, device, ticket, mutable provider identifiers, payloads,
and secrets. Platform Operations owns access, retention, export, and deletion.
